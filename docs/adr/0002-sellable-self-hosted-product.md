# ADR 0002: 판매용 제품 형태 — 고객사 설치형, 외부 모델 포함

- 상태: 채택 (2026-11-26)
- 관련: [ADR 0001](0001-local-llm-agent-control.md), [production-checklist](../production-checklist.md), [threat-model](../threat-model.md)

## 1. 배경

Tether는 지금 한 회사의 GPU 서버 한 대에서 시범 운영 중이다(`infra/staging/`). 이것을 다른 회사가 사서 직접 설치하고 운영하고 감사할 수 있는 제품으로 만든다.

PM, 아키텍트, 개발자, QA 관점 검토에서 세 가지가 출시를 막는 문제로 나왔다.
1. 배포 형태가 정해지지 않았다.
2. 신원과 키 관리가 수작업이다.
3. 설치, 업그레이드, 복구 경로가 없다.

이 ADR은 1을 결정하고, 2와 3의 방향을 정한다.

## 2. 결정

### P1. 고객사 서버에 설치하는 단일 고객 전용 제품이다
- 설치 하나가 고객사 하나다. 멀티테넌트와 우리가 호스팅하는 SaaS는 범위 밖이다.
- 고객사 데이터(프롬프트, 응답, 감사 기록, 키)는 고객사 밖으로 나가지 않는다. 우리는 운영 데이터에 접근하지 않는다.
- 그래서 DB 스키마에 테넌트 구분을 넣지 않는다. 한 고객사 안의 조직 구분은 그룹(IdP)과 정책으로 한다.

### P2. 모델 공급자는 자체 모델과 외부 모델 둘 다 지원한다
- 자체 모델: 고객사 GPU의 OpenAI 호환 서버(Ollama, vLLM 등). 지금의 `local` 공급자다.
- 외부 모델: Anthropic, OpenAI. llm-gateway에 이미 공급자로 있고, 회사 키는 게이트웨이만 갖는다.
- 어떤 경로든 같은 통제를 거친다: 세션 토큰, 정책의 모델 허용 목록, 가드레일, 내용 암호화 보관, 사용량 감사.
- 외부 모델은 인터넷 연결이 필요하다. 외부 모델을 쓰지 않는 고객을 위해 오프라인(air-gap) 설치도 지원한다.

### P3. 고객사마다 다른 부분은 교체 가능한 연결 지점으로 둔다
| 연결 지점 | 지금 | 제품에서 |
|---|---|---|
| 사람 신원 | 클라이언트 인증서(`AUTH_MODE=mtls`), OIDC 코드 있음 | **OIDC가 기본**(Google, Entra ID, Okta, Keycloak). 기기 인증서는 "등록된 기기인지" 확인에만 사용 |
| 그룹·퇴사 | 없음 | OIDC 그룹 claim(코드 있음) 다음으로 SCIM |
| 키 보관 | `.env`의 Fernet 키 한 개, 교체 불가 | 키 공급자 인터페이스: 파일, Vault, AWS KMS. 키 ID를 저장해 교체 가능하게 |
| 코드 저장소 | GitHub(App 토큰 브로커 코드 있음) | GitHub 먼저, GitLab은 수요 확인 뒤 |
| 클라우드 자격 | AWS STS 브로커 | 선택 기능. 없어도 제품이 동작해야 함 |
| 모델 | local, Anthropic, OpenAI | 그대로. Azure OpenAI·Bedrock은 수요 확인 뒤 |

### P4. 설치 단위는 컨테이너 묶음이고, 버전은 하나로 묶는다
- 한 번에 받는 설치 묶음(이미지, compose 또는 Helm, 설치 프로그램, 서명) 하나에 버전 번호 하나를 붙인다.
- 설치 프로그램 하나가 사전 점검, 설정 입력, 인증서 발급, 기동, 자기 점검을 한다. 지금의 `00`~`90` 스크립트를 이것으로 합친다.
- 업그레이드: 버전 사이 DB 마이그레이션은 앞으로만 가며 자동이다. 업그레이드 전에 자동으로 백업한다. 감사 해시 체인은 업그레이드를 거쳐도 이어진다.
- 첫 지원 대상: Ubuntu LTS 한 대(지금 구조) 다음으로 Kubernetes(Helm).

### P5. 보안 주장은 증거가 있는 것만 한다
- 샌드박스에는 프로그램 단위 실행 차단이 없다(OpenShell 한계). 판매 문서에는 실제로 강제되는 것만 적는다: 일반 사용자 실행, Landlock, 사이트·프로그램별 네트워크 제한, 이미지 고정.
- 가드레일은 규칙 기반이다. 평가 데이터셋으로 측정한 놓침률과 잘못 막은 비율을 릴리스마다 공개한다.
- 감사 기록의 무결성은 고객이 직접 검증할 수 있어야 한다(검증 도구와 절차 제공).

## 3. 이미 있는 것 (스테이징에서 켜지 않았을 뿐)
- OIDC 로그인과 그룹 claim(`AUTH_MODE=oidc`, `OIDC_*`)
- 외부 모델 공급자(Anthropic, OpenAI)와 회사 키 보관
- GitHub App 토큰 브로커, AWS STS 브로커(`services/credential-broker`)
- MDM 설정 생성기(`infra/mdm`), Claude Code를 게이트웨이에 고정하는 기능
- CI(`.github/workflows/test.yml`, `policy.yml`)
- 승인자와 요청자 분리(`SINGLE_ADMIN_APPROVAL`은 스테이징 예외)

## 4. 새로 만들어야 하는 것 (로드맵)

### 단계 A — 외부 고객 한 곳에 설치할 수 있게 (출시를 막는 것)
1. **설치 프로그램과 설치 묶음**: 사전 점검, 설정, 기동, 자기 점검. 깨끗한 VM에서 엔지니어 없이 하루 안에 끝나는 것이 완료 기준.
   - 2026-11-26 설계 확정: [설치 프로그램 설계](../install-design.md). 서비스 CA는 서버에서 생성하고 정책 서명 키만 분리, Ubuntu 24.04만, 서명된 오프라인 묶음.
   - 2026-11-26 첫 구현(`infra/installer/`, 설계 8절): 묶음 생성·서명, `tether-install` 10단계, `tether-doctor`, `tether-admin`. 깨끗한 Ubuntu 24.04 VM(`infra/testvm/install-test.sh`)에서 처음부터 설치 7분(설치 프로그램 42초), doctor 실패 0, e2e 32개 통과·실패 0(자체 모델 항목은 VM에 GPU가 없어 건너뜀). 남은 것: OIDC(A-4), 업그레이드(A-2), 설치 안내서, 인터넷 없는 설치 확인.
2. **업그레이드와 백업·복구**: 자동 백업, 마이그레이션, 복구 연습 절차.
3. **키 공급자와 키 교체**: 키 ID 저장, MultiFernet 방식 교체, 백업과 키 분리.
   - 2026-11-26: 키 묶음(`CONTENT_ENCRYPTION_KEYS`, 파일 `CONTENT_ENCRYPTION_KEYS_FILE`), 행마다 키 id(마이그레이션 0012), `python -m app.rekey`와 관리자 API. Vault·KMS 직접 연동과 백업에서 키 분리는 남음.
4. **OIDC를 기본으로**: 설치할 때 IdP 설정, 기기 인증서는 선택.
5. **외부 모델 경로 실사용 검증**: `tether claude`/`tether codex`를 샌드박스 이미지, 게이트웨이, 가드레일까지 끝까지 확인.
   - 2026-11-26: 이미지 `infra/sandbox-images/coding-agents`(Claude Code 2.1.332, Codex 0.172.0, 실행 파일은 `/usr/local/libexec/tether`), 실서버 e2e에서 두 에이전트 모두 샌드박스 → 프록시 → 게이트웨이 도달 확인. 정책 밖 모델은 403. 회사 키를 넣은 뒤 실제 응답 확인이 남음.
6. **CI 릴리스 게이트**: 단위 테스트, 깨끗한 VM 설치, e2e가 모두 통과해야 출고.
   - 2026-11-26: `release-gate.yml`(Postgres 스키마 검사, 이미지 빌드, compose smoke)과 [릴리스 기준](../release.md). 첫 실행에서 모델과 마이그레이션의 NOT NULL 불일치 19곳을 찾아 0013으로 맞춤. 깨끗한 VM 설치 검사는 A-1 뒤.
7. **서명**: macOS 런처 Developer ID 서명·공증, 컨테이너 이미지와 설치 묶음 서명.

### 단계 B — 고객 보안팀 심사를 통과하게
1. 최소한의 웹 관리 화면: 승인, 감사 조회, 긴급 차단, 정책 상태.
2. 사람별 일일 사용량 한도, GPU 대기열과 동시 실행 수 제한.
3. 가드레일 평가 데이터셋과 측정 결과.
4. 감사 기록 무결성 검증 도구.
5. 감시 지표와 알림(Prometheus 형식), SIEM 연동 안내.
6. 외부 모의해킹, 보안 백서, 위협 모델 공개판.

### 단계 C — 판매 운영
1. 라이선스 키와 사용자 수 측정.
2. 지원 체계, 버전 지원 기간, 보안 패치 공지 절차.
3. ISMS-P(국내) 또는 SOC 2(해외) 대응 자료.
4. OpenShell 의존성 확인: 라이선스, 유지보수 상태, 대체 계획.

## 5. 트레이드오프
- 설치형이라 고객사마다 환경이 다르다. 지원 비용을 줄이려면 지원하는 OS·GPU·IdP 조합을 좁게 시작한다.
- 멀티테넌트를 하지 않으므로 SaaS로 갈 때는 다시 설계해야 한다. 지금은 고객 데이터를 고객사 밖에 두지 않는다는 점이 판매 논리이므로 받아들인다.
- 외부 모델을 포함하면 인터넷 연결 설치와 오프라인 설치 두 가지를 테스트해야 한다.

## 6. 열린 질문
- 첫 고객의 IdP, Mac·Windows·Linux 비율, GPU 보유 여부.
- 가격 단위: 사용자 수, 서버 수, 사용량.
- Windows 런처 필요 여부.
